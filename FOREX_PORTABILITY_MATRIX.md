## Confirmed not to exist as separate engines (do not credit portability that was never built)
Volatility, Momentum, Reversal, and Regime are **not** dedicated research engines in this codebase — momentum/reversal/rank/zscore are *features* inside `cross_section_engine.py`; regime classification exists only in `bot.engines.regime_detector` (live execution, unrelated to research) and `feature_validator.py`'s `MarketRegimeDetector` (a labeling utility, not a standalone engine). Factor, lead-lag, dispersion, change-point, microstructure, market-impact, carry, on-chain, event-driven, alternative-data, sentiment, ML signal/regime, ensemble, portfolio optimization, and stress-testing engines also do not exist for Crypto, so there is nothing to "make portable" for Forex in any of these categories.

## Open finding — `entry_exit_engine.py`'s Sharpe annualization
`_compute_sharpe_from_equity_curve()` uses a hardcoded `np.sqrt(365)`, correctly justified for Crypto (24/7/365) but never made asset-class-aware via the `bot.instruments.periods_per_year()` infrastructure this same file already uses elsewhere for cost modeling. For Forex, the correct convention is not obvious without a real methodology decision: trading-day annualization (260, if weekend gap-risk should be excluded) vs. calendar-day annualization (365, if a strategy that holds positions over a weekend should be penalized for that real exposure). **Not fixed this mission** — this needs a deliberate choice, not a mechanical constant swap, and it is currently unreachable with real data anyway (zero Forex candidates survive the cointegration ladder, so no real equity curve has ever been computed for a Forex pair). Recorded as a named limitation, not silently left as a bug.
